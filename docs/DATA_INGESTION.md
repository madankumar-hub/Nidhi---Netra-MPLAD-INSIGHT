# Data ingestion

Where the data comes from today, and what it would take to point this at real
MPLADS records. This exists because "is this real data?" is the first question
a reviewer asks, and the answer should be precise rather than defensive.

## What is in the database today

A synthetic dataset, generated by `backend/seed/seed_data.py`. It is labelled
as synthetic in the footer of every page, in the footer of the PDF export, and
in a `data_source` column carried on **every row** of the CSV export — because a
CSV gets forwarded, renamed and opened by someone who never saw the page it came
from.

It is not arbitrary. The generator mirrors the real scheme's structure:

* MPLADS entitlement of ₹5 crore per MP per year, split across works whose
  sanctioned amounts follow the distribution seen in published district lists;
* the real work categories — roads, water supply, education, health,
  electrification, community infrastructure;
* real executing agencies (PWD, Zila Parishad, PHED, municipal bodies);
* sanction, start and planned-completion dates with realistic slippage;
* expenditure that lags physical progress the way it does in practice.

It also contains **deliberately injected anomalies** — cost overruns, stalled
reporting, near-duplicate sanctions in the same block — so that the detection
engine has something real to find during a demonstration. Without them, a
demo of an anomaly detector shows an empty list.

## Why not real data

MPLADS data is published, but not as anything you can consume directly:

* the MPLADS portal publishes per-constituency lists, largely as scanned or
  generated PDFs rather than a structured feed;
* `data.gov.in` carries MPLADS resources, but coverage is uneven across states
  and years, and schemas differ between resources;
* there is no public API that returns sanctioned works with expenditure and
  physical progress against a stable identifier.

So any real deployment starts with an extract, not a live feed. That shapes the
design below.

## How real data gets in

Three routes exist today, in increasing order of volume.

### 1. Single record — the works register

**Officials portal → Projects → New work.** For a record an officer is entering
by hand. Validated field by field, audited on save.

### 2. Bulk extract — CSV import (FR15)

**Officials portal → Projects → Bulk import.** Upload a CSV; the browser parses
it, reports the row count and every rejected row with its line number, and
nothing is sent until the reviewer accepts what they see. The API then
re-validates every row server-side — the browser check is a courtesy, not the
security boundary.

`samples/mplad-works-sample.csv` is a working example: ten works in Sirohi
district, Rajasthan. It imports with zero rejections, and every category,
executing agency and status in it is drawn from the same controlled vocabulary
the seeded data uses — so the imported works group, filter and translate exactly
like the other 600 rather than sitting alone in the dropdowns.
`backend/tests/test_sample_csv.py` fails the build if that stops being true.

Sirohi is deliberately **not** in the seeded dataset, so the import is visible:
the district has no works before it and ten after.

`samples/mplad-works-with-errors.csv` is the counterpart — six rows of which
four are rejected: a non-numeric amount, a non-numeric year, a non-numeric
progress figure and a row with a missing column. Every rejection names its line
number, and nothing is sent to the API until the reviewer accepts what they see.
It exists so the validation can be shown rather than described.

**Required columns**

```
title, mp_name, state, district, category, executing_agency,
sanction_year, allocated_amount
```

**Optional columns** — `constituency`, `block`, `contractor`, `spent_amount`,
`estimated_cost`, `progress_percent`, `planned_progress_percent`, `status`,
`beneficiaries`, `latitude`, `longitude`, `description`, `sanction_date`,
`start_date`, `planned_end_date`, `actual_end_date`, `photo_url`,
`document_url`, `remarks`.

Anything omitted falls back to a sensible default. `latitude` and `longitude`
are stored and served by the API; nothing in the current UI plots them, but
they are there for a future map or for an external consumer of the API.

### 3. Programmatic — the API

`POST /api/admin/projects/bulk-import` takes the same records as JSON and
returns created, skipped and per-row errors. Auditor or Administrator only.
This is what a scheduled adapter would call.

## What an adapter would add

The remaining work is a scheduled job, not a redesign. It would:

1. fetch the MPLADS resources for a state and year from `data.gov.in`;
2. map their column names onto the schema above (each resource differs, so this
   is a per-source mapping table, not one parser);
3. resolve each record to a stable key — work code where present, otherwise
   `(constituency, sanction_year, title)` — so that a re-run updates rather
   than duplicates;
4. geocode the location where coordinates are absent (optional - the schema
   accepts records without them);
5. call the bulk-import endpoint and record the run in the activity log.

Steps 1 and 4 need network access and an API key; steps 2, 3 and 5 are
ordinary application code. The honest estimate is a few days for one state,
and the per-source mapping table is the part that does not generalise.

## What this means for the risk engine

Nothing. The engine reads the `Project` model, not the seed script. A work
loaded from a real extract is scored by exactly the same rules, the same
cohort statistics and the same anomaly model as a seeded one — which is the
point of keeping ingestion and assessment separate.

Two caveats worth stating plainly:

* **Cohort statistics need volume.** The statistical layer compares a work
  against its peers in the same category and district, and the anomaly model
  needs at least 40 records in a cohort before it runs at all. A first import
  of one district will lean on the deterministic rules until the dataset fills
  out.
* **Detection quality follows data quality.** Fields that real extracts often
  leave blank — physical progress, expenditure dates — are exactly the ones
  several rules depend on. The engine reports a data-completeness percentage
  alongside every assessment for this reason: a low score means the record was
  thin, not that the work is clean.
